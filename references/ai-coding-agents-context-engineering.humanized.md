# Контекст и наблюдаемость для агентов, которые пишут код

Агенты, которые пишут код, уже не похожи на автодополнение в редакторе. В рабочих командах они всё чаще стоят между задачником, репозиторием, CI, pull request и ревьюером. Поэтому главный вопрос меняется: не “насколько умная модель?”, а “что агент видит, чем он может пользоваться и как мы потом разберём, что он сделал?”.

GitHub Copilot cloud agent хорошо показывает этот сдвиг. Агент может изучить репозиторий, составить план, сделать изменения в ветке, запустить тесты и линтеры во временном окружении на GitHub Actions. Это уже не диалог в IDE, после которого разработчик сам собирает ветку, коммит, описание PR и все остальные мелочи. Часть рутины уходит агенту.

Но вместе с этим появляются новые вопросы. Кто поставил задачу? Кто отвечает за результат? Кто решает, можно ли принять изменения? Где смотреть ход работы, если PR выглядит правдоподобно, но ломает контракт внутри системы?

Здесь и появляется управление контекстом, или context engineering. Это не “написать хороший запрос”. Агенту нужно собрать рабочую картину: инструкции репозитория, стиль кода, текст задачи, прошлые попытки, доступные инструменты, состояние ветки, результаты CI, комментарии ревьюеров, правила безопасности, ограничения по правам и стоимости. Если контекста мало, агент пишет общее решение. Если его слишком много, растут задержки и расходы, а модель начинает хуже отделять главное от шума. Если контекст устарел, агент уверенно чинит уже не ту систему.

Вторая опора — наблюдаемость. В обычном сервисе мы смотрим логи, метрики и трассировку запросов. У агента одной записи HTTP-запроса мало: ошибка может появиться на пятом шаге, после вызова инструмента, неудачной команды, неверного предположения или передачи работы другому агенту. OpenAI Agents SDK, например, пишет трассы с вызовами модели, инструментами, передачами между агентами, защитными правилами и пользовательскими событиями. OpenAI отдельно описывает trace grading: оценку не только финального ответа, но и пути, которым агент к нему пришёл.

С проверками та же история. Старому чат-боту можно было дать вопрос, сравнить ответ с эталоном и поставить балл. Для агента, который пишет код, этого мало. Anthropic предлагает смотреть на задачу, отдельные попытки, проверяющие правила, полную запись выполнения, итоговое состояние и инфраструктуру, которая всё это запускает. Агент может написать “готово”, но настоящий результат лежит в тестах, базе данных, интерфейсе или изменениях в коде. Хорошая проверка для такого агента — это репозиторий в известном состоянии, инструменты, песочница, тесты, статический анализ и иногда человек с рубрикой для спорных случаев.

Метрики тоже легко обмануть. Можно радоваться числу PR, скорости принятия изменений и росту использования. GitHub уже даёт метрики по жизненному циклу pull request для Copilot cloud agent. Но если смотреть только на скорость, команда может получить много мелких PR, которые потом долго чистят ревьюеры. Нужна более честная панель: сколько PR приняли, сколько вернули, как часто падал CI, сколько правил безопасности сработало, сколько правок внёс человек, сколько стоила принятая правка и какие ошибки повторяются в трассах.

Самое полезное наблюдение: агенты для кода не отменяют инженерную дисциплину, а делают её заметнее. Инструменты для агента нужно проектировать так же внимательно, как API для людей. Anthropic отдельно пишет про понятные границы инструментов, полезный контекст в ответах и экономию токенов. Плохой инструмент заставляет агента угадывать. Хороший инструмент объясняет, когда его вызывать, какие параметры безопасны, что означает ошибка и можно ли повторить действие.

В ближайшей версии этого мира агент может начинать работу, вести ветку и приносить PR. Но последнее слово остаётся за человеком. Свежие исследования PR, созданных агентами, показывают ровно это разделение: агент получает больше операционной самостоятельности, а право принять изменения почти всегда остаётся у людей.

Такой контур выглядит здраво. Агент быстро выполняет ограниченную работу. Команда видит его следы, проверяет результат и постепенно расширяет доверие. Без контекста, трассировки и проверок это просто генератор кода. С ними — участник инженерной системы, которого можно измерять, отлаживать и держать в границах.
