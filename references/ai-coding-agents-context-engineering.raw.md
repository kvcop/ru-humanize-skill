# Context engineering для AI coding agents в enterprise workflow

AI coding agents уже перестали быть просто autocomplete с более длинным context window. В нормальном enterprise setup они начинают работать как отдельный execution layer между backlog, repo, CI, pull request lifecycle и человеческим review. И вот тут внезапно выясняется, что главный bottleneck не в том, насколько smart модель, а в том, какой context ей дали, какие tools доступны, какие traces пишутся и есть ли вообще eval harness, который показывает, где агент реально fail’ится.

Если смотреть на GitHub Copilot cloud agent, там уже прямо описан workflow, где агент может research’ить repository, создавать implementation plan, делать changes на branch, запускать tests и linters в ephemeral GitHub Actions environment, а потом приносить всё это в pull request flow. Это сильно отличается от IDE assistant mode, где developer сидит локально, chat’ится с моделью, потом сам делает branch, commit, push, PR description и весь остальной ручной glue. В cloud-agent model часть этих manual steps становится автоматизированной, но зато появляется другой class проблем: кто дал task, кто author changes, кто отвечает за merge governance, как понять quality PR до человеческого review и где смотреть agent trajectory, если результат странный.

Context engineering в таком мире — это не “напишите хороший prompt”. Это сборка всего information payload, который агент видит перед action. Repo instructions, coding standards, issue text, previous attempts, tool schemas, memory, CI feedback, reviewer comments, branch state, relevant docs, security policy, permissions, cost limits — всё это становится частью agent operating environment. Если context слишком бедный, агент делает generic solution. Если context слишком жирный, начинается prompt stuffing, latency, cost spike и degraded reasoning. Если context stale, агент оптимизирует под старую архитектуру и потом уверенно открывает PR, который looks plausible, но ломает текущий contract.

Отдельный pain point — observability. В обычном сервисе у нас есть logs, metrics, traces. В agentic system одного HTTP trace уже мало, потому что проблема может быть не в одном request, а в multi-turn trajectory: model call, tool call, failed command, retry, hallucinated assumption, handoff to another agent, guardrail response, final diff. OpenAI Agents SDK, например, пишет tracing for LLM generations, tool calls, handoffs, guardrails и custom events. OpenAI eval docs отдельно push’ят trace grading, потому что black-box output eval часто не объясняет, почему агент прошёл или не прошёл task. Trace-level view даёт возможность смотреть не только final answer, но и path, которым агент к нему пришёл.

С evals похожая история. Для старого chatbot можно было дать prompt, проверить answer и поставить score. Для coding agent это почти всегда insufficient. Anthropic в agent evals описывает task, trial, grader, transcript или trace, outcome, evaluation harness и agent harness. Это важно, потому что агент может сказать “done”, но настоящий outcome лежит в database, repo, test results или UI state. Поэтому хороший eval для coding agent — это не просто LLM-as-judge над финальным текстом. Это sandbox, tool access, initial repo state, deterministic checks, maybe browser agent для UI, maybe static analysis, maybe unit tests, maybe human-labeled rubric для cases, которые нельзя поймать тестами.

Enterprise teams ещё любят говорить про productivity metrics, но здесь тоже легко self-deceive. Можно мерить number of PRs created by agent, median time to merge, adoption, merged PR rate. GitHub Copilot metrics прямо говорят про PR lifecycle outcomes. Но если мерить только throughput, можно получить много small PRs, которые reviewers потом долго clean up’ят. Поэтому нужен blended dashboard: PR throughput, review churn, revert rate, CI failure rate, security findings, human edit distance, time-to-merge, trace failure clusters и cost per accepted change. Иначе агент выглядит как performance win в executive dashboard, а на земле превращается в review tax.

Самое смешное, что agentic coding делает старые инженерные discipline ещё важнее. Tool descriptions нужно prompt-engineer’ить почти как user prompts. Anthropic пишет, что tools должны быть clearly defined, возвращать meaningful context и быть token-efficient. MCP и похожие protocols дают удобный tool layer, но если tool names, schemas и responses плохо спроектированы, агент начинает guess’ить. Хороший tool for agent — это не просто API wrapper. Это affordance: агент должен понять, когда tool использовать, какие параметры безопасны, что значит error, можно ли retry, destructive ли operation и какой context вернуть обратно в loop.

В итоге enterprise AI coding workflow упирается в governance. Новые исследования по agent-authored PR lifecycles показывают, что operational agency и merge authority расходятся: агент может инициировать и вести PR, но final merge decision почти всегда остаётся у человека. Это, скорее всего, правильный shape на ближайшее время. Агент может быть быстрым execution worker, но human still owns product judgement, architecture trade-offs, security boundary и responsibility перед пользователями.

Поэтому “внедрить AI coding agents” — это не купить еще один license и сказать команде “use agents”. Это построить контекстный pipeline, observability layer, eval suite и governance loop. Без этого агент просто генерирует more code. С этим он начинает становиться нормальным участником engineering system, которого можно дебажить, измерять, ограничивать и постепенно допускать к более сложным tasks.
